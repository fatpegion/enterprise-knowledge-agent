# 方案

每一步模型收到当前问题、历史、工具观察和剩余步数，从 `search`、`read`、`finish` 中选一个动作。执行器校验动作和参数，调用工具，将结构化结果送回模型。模型可以在空结果后改写查询，在发现矛盾后补查适用范围，也可以结束并请求澄清。执行器负责预算、引用来源和状态形状的检查。

| 模块 | 职责 |
| --- | --- |
| [main.py](../src/main.py) | JSON 输入检查、模型选择、CLI 输出 |
| [agent.py](../src/agent.py) | 动作白名单、观察回传、原文缓存、引用与状态校验、步数上限 |
| [knowledge.py](../src/knowledge.py) | 本地检索和原文读取，提供检索或读取故障注入 |
| [models.py](../src/models.py) | JSON 动作协议、真实 HTTP 模型适配、离线测试替身 |

检索对词条做大小写和标点归一化。标准词命中得 3 分，配置同义词命中得 2 分。累计评分后返回候选 ID、版本、命中词和片段 ID。检索结果没有正文。只有本轮已检索到的片段可读取，且引用原文由执行器从成功的读取结果原样复制。限制在小资料集上保留了可解释的命中依据，也便于用 `--no-aliases` 对照检索效果。

冲突场景中，D01 与 D02 的正文不同且没有生效优先关系。模型应查找管辖范围、例外或优先级，补查仍无消歧依据时返回 `conflict`。日期作为溯源信息。明确作答前，执行器检查已命中且与引用文档同属一个 `policy_topic` 的候选是否已读取。这个可选标签描述制度事项，供维护者把可能互相覆盖的制度归组。提交冲突结论前，执行器检查引用至少两份文档且读取后有补查。执行器向模型回传不通过的原因，后续模型决策计入同一个步数预算。答案与原文的语义支持仍由模型判断与评估样例核验。

首轮检索为空且模型要以资料不足结束时，执行器返回反馈，模型可以改写查询或追问。对最终的资料不足状态，执行器将对员工的回复限定在当前知识库的覆盖范围内，并保留模型给出的具体证据缺口。

最终冲突回复附上联系制度负责人确认适用规则的提示。冲突内容、两份原文的引用和未解决的证据缺口来自模型的结论与本轮工具结果。

采用 Python 标准库实现协议和本地工具，模型通过 Chat Completions HTTP 接入。搜索、读取、输出预算和校验均可脱离第三方框架复现。模型出错或返回非法决定时，CLI 给出 `model_error`。工具故障作为观察回传，模型可以尝试其他有效查询或结束。每个步骤保留一句可审计的动作依据。

本地复跑使用 `node-llama-cpp` 3.22.3 负责权重加载、上下文、CPU 推理和 JSON 语法约束。复跑用 HTTP 桥接负责将 CLI 请求交给推理库。它只监听本机，采用单并发。动作选择由模型承担，检索和证据校验由 Python CLI 承担。[推理库文档](https://node-llama-cpp.withcat.ai/guide/)
